My work ensured that students and administrators could use the platform safely while keeping sensitive verification details and session states properly controlled.What I built (files, features, commits)Across the repository, my contributions centered on the architecture wiring, session/RBAC security layer, and project documentation:Architecture & Express Setup (server/src/app.js, server/src/config.js, server/src/db.js, client/src/api.js, client/src/auth.jsx): Structured the React-to-Express-to-MySQL flow, same-origin API client (credentials: 'same-origin'), production build serving (client/dist), helmet security headers, JSON body limits, and MySQL connection pooling with transaction support (withTransaction).Folder Layout & Database Schema (database/schema.sql, server/, client/, docs/): Organized the codebase into modular layers (database/, server/src/middleware/, server/src/routes/, client/src/, docs/) and defined relational tables (users, sessions, reports, claims) with foreign keys and generated unique indexes.Authentication, Role Guards & Private Field Controls (server/src/middleware/auth.js, server/src/routes/auth.js, server/src/routes/reports.js, server/src/routes/claims.js, server/src/routes/admin.js): Implemented bcryptjs password hashing, constant-time login verification via a dummy hash, rate limiting on auth routes, SHA-256 hashed session tokens in HttpOnly cookies, server-side role/ownership checks (requireAuth, requireStudent, requireAdmin), allow-listed public report columns (PUBLIC_COLS), restricted identifying_details and claim evidence visibility, and raw image magic-byte checks (hasImageSignature).   Decisions I made and whyServer-backed HttpOnly session tokens over stateless JWTs: I stored cryptographically random session tokens in an HttpOnly, SameSite=Strict cookie (ucu_sid) while keeping only their SHA-256 hash in MySQL sessions. This allows logging out to delete the session row and revoke access immediately, and avoids exposing bearer tokens to client-side scripts.Explicit allow-lists and server-enforced RBAC/ownership checks: Rather than relying on frontend hiding alone, I enforced roles (student vs. admin) and ownership checks on every protected route, restricted registration to student, and used explicit column selection (PUBLIC_COLS) plus conditional response fields so identifying_details and claim evidence only reach authorized users.Transactions, row locks, and database constraints for claims: To prevent race conditions—such as two simultaneous approvals or duplicate live claims on an item—I combined withTransaction (SELECT ... FOR UPDATE) with generated unique indexes in MySQL.Challenges and how I solved themPreventing race conditions and rule bypasses on claims and returns: Concurrent claim submissions or approvals could conflict if handled non-atomically. I wrapped claim creation, approval, and return confirmation inside MySQL transactions using FOR UPDATE locks and added generated unique columns (uq_one_approved_per_item and uq_one_live_claim_per_student) as a database-level backstop.Avoiding accidental leakage of private fields and spoofed uploads: Public listings and claim responses needed to stay informative without exposing identifying_details, reporter identity, or claim evidence, while image uploads needed protection beyond file extensions or MIME headers. I separated public column projections from owner/admin-only fields and added magic-byte verification (hasImageSignature) for JPG, PNG, and WebP files.

What I learned / what I would do differently

Working on this project reinforced how important defense-in-depth is: pairing clean folder boundaries and clear user workflows with server-side authorization, safe session handling, and database-enforced invariants prevents entire classes of bugs. If I were building this again from scratch, I would document architectural decisions and API contracts earlier in the docs/ folder as features evolve, and consider structured audit logging for administrative decisions and return confirmations.
